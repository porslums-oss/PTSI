PTSI-Accounting — พอร์ตเป็น PostgreSQL + Node.js

ระบบบัญชีชุดเดิม (Oracle APEX App 151494) สร้างขึ้นใหม่ทั้งชุดบน PostgreSQL 16 — ตรรกะธุรกิจอยู่ในฐานข้อมูลทั้งหมด, REST API เป็นชั้นบางๆ ผ่านเข้าไป, และ Web UI แบบไม่มี build step เดียวกับแนวทางของ Smart ER

Database Schemadb/00_create_db.sql, 01_schema.sql, 03_views_security.sql, 07_audit_triggers.sql — schema เดียวชื่อ "acct"

ย้ายทุกตารางจากระบบ Oracle APEX เดิม (customers, quotations, invoices, receipts, purchase_requests/orders, journal_entries ฯลฯ) มาเป็น PostgreSQL พร้อมโมเดลสิทธิ์แบบ least-privilege 3 ระดับ

สามระดับสิทธิ์ (Role)ทุก role ตั้ง search_path = acct, public อัตโนมัติ

Required
acct_owner — เจ้าของ schema, รัน DDL ทั้งหมด acct_app — สิทธิ์ EXECUTE บน fn_* + SELECT บน view/master data เท่านั้น acct_report — SELECT อย่างเดียวทุกตาราง ยกเว้น app_user/app_session
ไม่มีสิทธิ์เขียนตรง:  acct_app (role ที่ Node.js API ใช้เชื่อมต่อจริง) ไม่มีสิทธิ์ INSERT/UPDATE/DELETE บนตารางธุรกรรมเลยแม้แต่ตัวเดียว — ทุกการเขียนข้อมูลต้องผ่านฟังก์ชัน fn_* เท่านั้น (ดูหัวข้อถัดไป) ทดสอบยืนยันแล้วว่า INSERT ตรงจาก acct_app ถูกปฏิเสธด้วย permission denied จริง

กลุ่มตารางหลัก (39 ตาราง)

Foundation
ข้อมูลหลัก: customers, vendors, employees, items, chart_of_account_* ขาย/ลูกหนี้: quotations, delivery_notes, invoices, billing_notes, receipts ซื้อ/เจ้าหนี้: purchase_requests, purchase_orders บัญชีแยกประเภท: journal_entries, journal_entry_lines, system_gl_mappings ภาษี: tax_rates, tax_filings, tax_filing_details ระบบ: app_user, app_session, setting, audit_log

Business Logic — fn_* Functionsdb/02_functions.sql — 31 ฟังก์ชัน PL/pgSQL, จุดเขียนข้อมูลเพียงจุดเดียวของทั้งระบบ

ตรรกะทางบัญชีทั้งหมด (เลขที่เอกสาร, VAT, การผ่านรายการเข้าบัญชีแยกประเภทแบบ debit=credit เสมอ) อยู่ในฟังก์ชันเหล่านี้ — ไม่ใช่ในโค้ด Node.js

#กลุ่มฟังก์ชันหลักทำอะไร
1Authfn_login / fn_session / fn_logout / fn_user_createล็อกอินด้วย token (ไม่ใช้ cookie), เก็บ session ใน app_session
2Settingsfn_setting / fn_setting_setค่าตั้งค่าระบบแบบ key/value
3Master Datafn_customer_upsert, fn_vendor_upsert, fn_item_upsert, fn_employee_upsert, fn_account_upsertเพิ่ม/แก้ไขข้อมูลหลัก — แยก insert/update จากการมี id ใน payload
4ใบเสนอราคาfn_quotation_create, fn_quotation_set_status, fn_quotation_jsonออกเลขที่อัตโนมัติ (Q-<category>-0001), คำนวณ VAT, บังคับต้องมีเลข PO ลูกค้าก่อนเปลี่ยนเป็น ACCEPTED
5ใบแจ้งหนี้fn_invoice_create_from_quotation, fn_invoice_postสร้างจากใบเสนอราคาที่ ACCEPTED แล้ว, ผ่านรายการเข้า GL แบบสมดุล (debit AR / credit VAT+รายได้)
6ใบเสร็จรับเงินfn_receipt_create, fn_receipt_postรองรับ 2 แบบ — รับชำระตามใบแจ้งหนี้ (CREDIT_COLLECTION) และขายสดออกใบเสร็จทันที (CASH_SALE)
7จัดซื้อfn_pr_create, fn_pr_set_status, fn_po_create_from_prใบขอซื้อ → ใบสั่งซื้อ (สร้างตรงได้โดยไม่ผ่าน PR)
8ภาษีfn_tax_filing_generate, fn_tax_rate_upsertสรุปยอดยื่นภาษี PP30 (VAT ขาย-ซื้อ) และ PND3/PND53 (หัก ณ ที่จ่าย) รายเดือน + master อัตราภาษี
9ข้อมูลบริษัทfn_company_profile_upsertข้อมูลบริษัทผู้ออกเอกสาร (ปกติมีแถวเดียว) รวมอัปโหลดตราประทับเป็น bytea
10ใบส่งของfn_delivery_note_create, fn_delivery_note_set_statusออกเลขที่ DN-YYYYMMDD-NNNNN, คัดลอกรายการจากใบเสนอราคาอัตโนมัติถ้าไม่ระบุรายการเอง
11ใบวางบิลfn_billing_note_create, fn_billing_note_set_statusรวมหลายใบแจ้งหนี้ของลูกค้ารายเดียวกันเข้าใบวางบิลใบเดียว ออกเลขที่ BN-YYYYMMDD-NNNNN
12GL Mappingfn_gl_mapping_setผูก control account (เช่น AR_CONTROL, VAT_OUTPUT) กับรหัสบัญชีจริงในผังบัญชี — ใช้ตอน auto-post journal
13ไฟล์แนบfn_attachment_upload, fn_attachment_deleteแนบไฟล์ (เก็บเป็น bytea) เข้ากับเอกสารได้ 8 ประเภท (quotations, delivery_notes, invoices, billing_notes, receipts, purchase_requests, purchase_orders, tax_filings)

กติกาการแจ้ง errorทุกฟังก์ชันใช้รูปแบบเดียวกัน แปลงเป็น HTTP status ฝั่ง Node ได้อัตโนมัติ

Critical
PL/pgSQL
RAISE EXCEPTION 'ERROR_CODE: ข้อความภาษาไทยอธิบายสาเหตุ';
-- เช่น: 'PO_REQUIRED: ต้องระบุเลขที่/วันที่ใบสั่งซื้อลูกค้าก่อนตั้งสถานะ ACCEPTED'
--       'ALREADY_POSTED: ใบแจ้งหนี้ INV-20260926-00001 ถูกลงบัญชีแล้ว'
ฝั่ง Node (server.js) ใช้ regex /^([A-Z_]+):\s*(.*)$/s แยกโค้ดหน้า ":" ออกมาก่อนข้อความ แล้ว map เข้า HTTP status ผ่านตาราง ERR_STATUS — โค้ดใหม่ที่ฐานข้อมูล raise เพิ่ม (เช่น DUPLICATE_CODE, *_NOT_FOUND, GL_MAPPING_MISSING) ต้องเพิ่มเข้าตารางนี้ด้วยไม่เช่นนั้นจะตกไปเป็น HTTP 400 ทั่วไปเสมอ

Audit Trail อัตโนมัติdb/07_audit_triggers.sql — trigger เดียวใช้ร่วมกัน 12 ตาราง

Foundation
fn_audit_trigger() — generic, SECURITY DEFINER customers, vendors, employees, items, chart_of_account_details, setting quotations, invoices, receipts, purchase_requests, purchase_orders, journal_entries, tax_filings company_profile, delivery_notes, billing_notes, system_gl_mappings, tax_rates
ทุกฟังก์ชัน fn_* ที่เขียนข้อมูล ตั้งค่า PERFORM set_config('acct.audit_user', p_by, true) เป็นบรรทัดแรกหลัง BEGIN — เป็น session variable แบบ transaction-local (is_local=true) ที่ trigger อ่านออกมาใช้เป็น changed_by จึงรู้ว่า "ใคร" เป็นคนสั่งเขียนแม้ว่า role จริงที่เชื่อมต่อฐานข้อมูลจะเป็น acct_app เสมอก็ตาม แต่ละแถวที่ INSERT/UPDATE/DELETE จะถูกบันทึกเป็น jsonb เต็มแถว (ก่อน/หลัง) ลงตาราง audit_log — อ่านได้จาก role acct_report เท่านั้น (ยังไม่เปิด endpoint ให้ตัวแอปดึงมาแสดงในเว็บ)
ไม่ครอบคลุมทุกตาราง:  ตั้งใจไม่ผูก trigger กับ app_user/app_session (มี password_hash/token ไม่ควรถูกคัดลอกเข้า audit log) และไม่ผูกกับตารางรายการย่อย เช่น quotation_items/po_items (ตรวจสอบย้อนกลับผ่านตารางหัวเอกสารได้อยู่แล้ว เพื่อไม่ให้ log รกเกินไป) รวมถึงไม่ผูกกับ document_attachments เพราะมีคอลัมน์ file_content เป็น bytea ก้อนใหญ่ — คัดลอกซ้ำเข้า audit_log จะทำให้ฐานข้อมูลบวมโดยไม่จำเป็น

Node.js APIapp/server.js — Express + pg เท่านั้น ไม่มี framework อื่นเพิ่ม

ชั้นบางๆ ที่แปลง HTTP request เป็นการเรียก SELECT fn_*(...) หรือ SELECT * FROM view/table ตรงๆ — ไม่มี business logic ซ้ำซ้อนกับฝั่งฐานข้อมูล

รูปแบบ Endpoint63 endpoint ทั้งหมดผ่าน middleware เดียวกัน

Required
POST /api/auth/login → fn_login GET /api/quotations → v_quotation_open POST /api/quotations → fn_quotation_create POST /api/invoices/:id/post → fn_invoice_post GET /api/dashboard/kpi → v_dashboard_kpi GET/POST /api/company-profile, GET /api/company-profile/stamp → fn_company_profile_upsert GET/POST /api/delivery-notes, POST /:id/status → fn_delivery_note_create/set_status GET/POST /api/billing-notes, GET /available-invoices/:customerId → fn_billing_note_create/set_status GET/POST /api/tax-rates, GET /api/tax-filings/:id → fn_tax_rate_upsert GET/POST /api/gl-mappings → fn_gl_mapping_set GET /api/journal-entries[/:id] → journal_entries + journal_entry_lines (อ่านอย่างเดียว) GET/POST/DELETE /api/attachments, GET /:id/download → fn_attachment_upload/delete
Auth ใช้ Bearer token ธรรมดา (ไม่ใช่ cookie/session ฝั่ง Express) — ทุก request ที่ผ่าน /api/* (ยกเว้น login/health) เรียก fn_session(token) ตรวจสอบทุกครั้ง จึงไม่มี session state ค้างอยู่ฝั่ง Node เลย, restart server ได้โดย client ไม่หลุด

Web UIapp/public/index.html — ไฟล์เดียว, vanilla JS, ไม่มี build step

SPA แบบ tab-based เหมือนแนวทาง Smart ER — string concatenation ธรรมดา ไม่ใช้ framework, เปิดได้ทันทีจากไฟล์ static ที่ Express serve ให้

Dashboard — KPI การ์ด + Trial Balance Quotations — สร้าง/ดู/เปลี่ยนสถานะใบเสนอราคา + ไฟล์แนบ Delivery Notes — ใบส่งของ คัดลอกรายการจากใบเสนอราคาอัตโนมัติ + เปลี่ยนสถานะ + ไฟล์แนบ Invoices — สร้างจากใบเสนอราคาที่ ACCEPTED + Post to GL Billing Notes — เลือกลูกค้าแล้วติ๊กเลือกใบแจ้งหนี้ที่ยังไม่วางบิลมารวมเรียกเก็บ + ไฟล์แนบ Receipts — รับชำระ (CREDIT_COLLECTION) และขายสด (CASH_SALE) Purchase Requests — สร้างใบขอซื้อ + เปลี่ยนสถานะ (DRAFT→PENDING→APPROVED/REJECTED→CLOSED) Purchase Orders — สร้างจากใบขอซื้อที่ APPROVED (คัดลอกรายการอัตโนมัติ) หรือสร้างตรง Tax Filings — สร้างแบบยื่นภาษีรายเดือน (PP30/PND1/PND3/PND53) + ดูรายการเอกสารประกอบ + ไฟล์แนบ Journal Entries — เบราว์สมุดรายวันที่เกิดจาก Post to GL อัตโนมัติ พร้อม badge Balanced/Unbalanced Account Mappings — ผูก control account (AR_CONTROL, VAT_OUTPUT ฯลฯ) กับผังบัญชีจริง (ADMIN) Master Data — Customers/Vendors/Items/Employees/Chart of Accounts/Tax Rates Company Profile — ข้อมูลบริษัทผู้ออกเอกสาร + อัปโหลดตราประทับ (ADMIN แก้ไข) Settings — ค่าตั้งค่าระบบ (แก้ได้เฉพาะ ADMIN)
Purchase Order — ยังไม่มีปุ่มเปลี่ยนสถานะ:  ฟังก์ชันฝั่งฐานข้อมูลยังมีแค่ fn_po_create_from_pr (สร้าง PO) ไม่มีฟังก์ชันสำหรับเปลี่ยนสถานะ PO (เช่น SENT → CONFIRMED → RECEIVED) จึงยังไม่ใส่ปุ่มเปลี่ยนสถานะในหน้าจอ — ต่างจาก Purchase Request ที่มี fn_pr_set_status ให้ใช้ครบแล้ว
ไฟล์แนบ (Document Attachments) เป็น widget ใช้ร่วมกัน:  ฟังก์ชัน JS attachmentsWidgetHtml(refTable, refId) เรียกใช้ในหน้ารายละเอียดของ Quotations, Delivery Notes, Billing Notes และ Tax Filings — อัปโหลดผ่าน FileReader แปลงเป็น base64 แล้วส่งเข้า fn_attachment_upload, ดาวน์โหลดผ่าน endpoint ตรงๆ (/api/attachments/:id/download) ไม่ผ่าน JSON

จุดที่แก้ไข (Reconciliation)

ฐานข้อมูลกับแอปถูกสร้างคู่ขนานจากสเปกเดียวกันโดยไม่เห็นผลงานสุดท้ายของกันและกัน จึงเกิดจุดที่ไม่ตรงกันหลายจุด — ทั้งหมดถูกตรวจพบและแก้ไขแล้ว พร้อมทดสอบยืนยันด้วยฐานข้อมูลจริง

ช่องโหว่ที่สำคัญที่สุด: สิทธิ์การเขียนข้อมูลใช้งานจริงไม่ได้เลยfn_* ไม่ได้ตั้งเป็น SECURITY DEFINER

Critical
อาการ:  ฟังก์ชันทุกตัวถูกทดสอบผ่านหมดตอนพัฒนา แต่ทดสอบในฐานะ acct_owner (เจ้าของ schema) เท่านั้น — พอเปลี่ยนมาเชื่อมต่อด้วย acct_app (role จริงที่ Node.js API ใช้) กลับเจอ permission denied ในการ login และทุกฟังก์ชันที่เขียนข้อมูล เพราะฟังก์ชัน PL/pgSQL แบบปกติจะรันด้วยสิทธิ์ของ "ผู้เรียก" ไม่ใช่สิทธิ์ของ "เจ้าของฟังก์ชัน" — และ acct_app มีแค่สิทธิ์ SELECT บนตาราง ไม่มีสิทธิ์ INSERT/UPDATE/DELETE เลย ทางแก้:  เพิ่ม SECURITY DEFINER SET search_path = acct, public ให้ทุกฟังก์ชันทั้ง 22 ตัว (รันด้วยสิทธิ์ของ acct_owner ที่เป็นเจ้าของฟังก์ชันเสมอ ไม่ว่าใครจะเรียก) และเพิ่ม GRANT USAGE ON SCHEMA public TO acct_app, acct_report ใน 00_create_db.sql (ฟังก์ชัน crypt()/gen_random_bytes() ของ pgcrypto อยู่ใน schema public) — ทดสอบยืนยันแล้วว่า login และทุก endpoint ที่เขียนข้อมูลใช้งานได้จริงตอนนี้ ขณะที่การ INSERT ตรงจาก acct_app ยังถูกปฏิเสธเหมือนเดิม (โมเดลความปลอดภัยยังครบ)

ข้อควรระวัง (สรุปจากที่เจอจริง)

  • !SECURITY DEFINER: ฟังก์ชันเขียนข้อมูลทุกตัวต้องมี SECURITY DEFINER SET search_path = acct, public มิฉะนั้น role ของแอป (acct_app) จะเรียกใช้ไม่ได้เลยแม้จะมีสิทธิ์ EXECUTE (หัวข้อที่ 6)
  • !schema public: ถ้า REVOKE ALL ON SCHEMA public FROM PUBLIC โดยไม่ regrant USAGE ให้ role ของแอป ฟังก์ชันของ pgcrypto (crypt/gen_random_bytes ที่ fn_login ใช้) จะเรียกไม่ได้ (หัวข้อที่ 6)
  • !psql :variable ใน DO $$ ... $$: ไม่ interpolate ภายใน dollar-quoted body — ต้องสร้างข้อความ DO block ด้วย format(..., %L) ที่ระดับบนสุดก่อน แล้วค่อยรันข้อความนั้น (พบใน 05_smoke_test.sql)
  • !ชื่อคอลัมน์ระหว่าง 2 ทีมงาน: เมื่อฐานข้อมูลกับแอปสร้างคู่ขนานจากสเปกเดียวกัน ต้องไล่เทียบชื่อ column/jsonb key ทุกจุดจริงๆ ก่อนส่งมอบ — เอกสารสเปกอย่างเดียวไม่พอ (หัวข้อที่ 6)
  • !ทดสอบด้วย role จริง: การทดสอบด้วย acct_owner (เจ้าของ schema) ไม่เพียงพอ ต้องทดสอบด้วย role ที่แอปจริงใช้เชื่อมต่อ (acct_app) เพื่อให้เจอปัญหาสิทธิ์ตั้งแต่ตอนพัฒนา ไม่ใช่ตอน production
