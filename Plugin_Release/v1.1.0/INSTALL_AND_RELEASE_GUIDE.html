ผู้ดูแล plugin (Maintainer)

  • แก้ไข / เพิ่มความสามารถ
  • ผ่าน release gate แล้วออกเวอร์ชัน
  • แจกไฟล์ .plugin + release notes
  • เก็บ .plugin เวอร์ชันก่อนไว้ rollback

DBA ผู้ใช้งาน

  • ติดตั้ง / อัปเดต plugin ใน Cowork
  • ดูแล workspace ของตัวเอง (config + work)
  • ตรวจและอนุมัติรายงานทุกฉบับ

DB server ของลูกค้า

  • รัน collector (read-only) ตามเวลา
  • ส่งไฟล์ .dck / .mck มายัง inbox
  • อัปเดต collector เมื่อ release มีป้าย COLLECTOR

1ติดตั้ง plugin (DBA ผู้ใช้งาน · ครั้งแรก)

  1. เตรียมเครื่อง
    Claude desktop (Cowork) · Python 3.8 ขึ้นไป · pip install --user openpyxl python-docx · สร้างโฟลเดอร์ workspace เช่น D:\DBA_Ops (ไม่ควรอยู่ในโฟลเดอร์ที่ sync ขึ้น cloud สาธารณะ)
  2. ติดตั้งไฟล์ dba-ops.plugin
    รับไฟล์จากผู้ดูแล plugin (ช่องทางภายในองค์กรเท่านั้น) → ลากหรือแนบไฟล์ลงในแชทของ Cowork → กดปุ่มติดตั้ง/ยอมรับ plugin บน preview ที่แสดงขึ้นมา ถ้าองค์กรใช้ plugin marketplace ให้ติดตั้งผ่าน marketplace แทน
  3. เชื่อมโฟลเดอร์ workspace
    ใน Cowork เลือก "Add folder" แล้วเลือกโฟลเดอร์ workspace (หรือโฟลเดอร์แม่)
  4. ติดตั้ง kit ลง workspace
    พิมพ์ "ติดตั้ง DBA Ops ที่โฟลเดอร์ DBA_Ops" → Claude (skill dba-ops-setup) จะคัดลอก kit ลง DBA_Ops\kit และตรวจว่ามี Python library ครบ
  5. เพิ่มลูกค้าและระบบ
    พิมพ์ "เพิ่มลูกค้า ABC ชื่อ ABC Co., Ltd." แล้วต่อด้วย "เพิ่มระบบ SALESDB เป็น Oracle RAC 2 node host salesdb01, salesdb02" Claude จะสร้าง config\ABC.json ให้ (สิทธิ์ 600)
  6. ตรวจว่าติดตั้งสำเร็จ
    พิมพ์ "ทดสอบ DBA Ops ด้วยไฟล์ตัวอย่าง" → ต้องได้ Daily Status Report และ Routine Checklist ตัวอย่าง จากนั้นลบผลทดสอบออก

2Deploy ไปยังลูกค้า (collector บน DB server)

  1. ขออนุมัติ
    เปิด Standard Change กับลูกค้า (สคริปต์ read-only + cron) ระบุ host, เวลา, ช่องทางส่งไฟล์ และผู้รับผิดชอบ
  2. ให้ Claude เตรียม bundle
    พิมพ์ "เตรียม collector ของ SALESDB" → ได้โฟลเดอร์ work\ABC\deploy\SALESDB\ พร้อม collector.conf ที่ตั้งค่าแล้ว (ไม่มี password)
  3. สร้าง monitor user สิทธิ์ต่ำ
    ใช้สคริปต์ setup_monitor_*.sql ของ engine นั้น (Oracle ใช้ / as sysdba ได้ แต่แนะนำ c##dbaops + wallet สำหรับ DB ที่ OPEN)
  4. ติดตั้งและทดสอบบน server
    chmod 700 collector; chmod 600 collector.conf → รัน daily_check ด้วยมือ → python3 validate_dck.py <file> ต้องได้ OK → ตั้ง cron (daily 08:00, monthly วันที่ 1 08:30) · RAC: FULL 1 node, OS_ONLY node อื่น
  5. ตั้งช่องทางส่งไฟล์
    PAR ของ OCI แบบ เขียนอย่างเดียว + มีวันหมดอายุ + แยก prefix ต่อระบบ หรือ scp/copy มือ → ไฟล์ต้องมาถึง work\ABC\inbox
  6. รอบแรก
    พิมพ์ "รัน daily ของ ABC" แล้วตรวจว่าไม่มีรายการ "collection error" ที่ยังไม่รู้สาเหตุ

3ข้อควรปฏิบัติ ก่อน และ หลัง deploy ทุกครั้ง

ก่อน deploy

BEFORE
  • ได้รับอนุมัติ change จากลูกค้าแล้ว
  • ทดสอบบน non-prod ของ engine/version เดียวกันแล้ว (Oracle, SQL Server ต้องทำทุกครั้งจนกว่าจะผ่านการใช้งานจริง)
  • ใช้ user สิทธิ์ต่ำ ไม่ใช้ root, ไม่มี password ใน collector.conf หรือสคริปต์
  • OUT_DIR เป็นโฟลเดอร์ส่วนตัว (ไม่ใช่ /tmp) และ collector.conf สิทธิ์ 600
  • ตรวจ license: Oracle เปิด USE_DIAG_PACK=Y เฉพาะเมื่อมี Diagnostics Pack
  • PAR สร้างใหม่สำหรับลูกค้ารายนี้: write-only, มีวันหมดอายุ, ไม่ใช้ร่วมกับลูกค้าอื่น
  • ปรับ threshold ใน config ให้ตรงกับ SLA ในสัญญา
  • bundle สะอาด: ไม่มี work/ หรือ config ของลูกค้ารายอื่นปนมา

หลัง deploy

AFTER
  • ไฟล์แรกผ่าน validate_dck.py และถูกประมวลผลโดยไม่มี REJECT
  • ทุก host ส่งไฟล์ครบ (รายงานไม่มี "ไม่ได้รับไฟล์จาก …")
  • collection error ทุกรายการรู้สาเหตุ (สิทธิ์, feature ที่ไม่ได้ใช้) และบันทึกไว้
  • ค่าในรายงานตรงกับของจริง: สุ่มเทียบ 3–5 ค่ากับการ query ด้วยมือ (tablespace, backup, lag)
  • บันทึก CR id, collector version, host, วันที่ ลง Change_Log ใน Register
  • สิทธิ์ไฟล์บน server: ls -l collector 700, conf 600, output 750/640
  • ติดตาม 7 วันแรก ทุกวัน แล้วค่อยลดเป็นตรวจเฉพาะ Red/Amber

5ข้อควรปฏิบัติ ก่อน และ หลัง update ทุกครั้ง

ก่อน update — Maintainer

RELEASE
  • แก้บนสำเนา ไม่แก้ plugin ที่ติดตั้งใช้งานอยู่
  • ทำตามกฎความปลอดภัย ของ SECURITY_REVIEW (config parse, ไม่มี secret ใน argv, xlsafe, escape HTML, CSP)
  • เวอร์ชันตรงกัน 3 จุด: plugin.json, kit/VERSION, CHANGELOG (+ COLLECTOR_VERSION ถ้าแก้ collector)
  • CHANGELOG มีหัวข้อ Added / Changed / Fixed / Security, ป้าย BREAKING / COLLECTOR และ Upgrade steps
  • release_check.py ต้องได้ RELEASE OK 7/7
  • แก้ collector → ทดสอบกับ non-prod จริงของ engine นั้น แล้ว validate output
  • ไม่มีข้อมูลลูกค้า, ชื่อ host, PAR หรือ password ใน samples / templates / docs
  • เก็บ .plugin เวอร์ชันก่อนไว้สำหรับ rollback

ก่อน update — DBA ผู้ใช้

USER
  • อ่าน release notes ว่ามี BREAKING / COLLECTOR ไหม
  • ไม่ update ระหว่างงานสำคัญ (incident เปิดอยู่, ช่วงทำ monthly report)
  • ประมวลผล inbox ให้เสร็จก่อน (รัน daily รอบล่าสุด)
  • สำรอง config\ และ work\<CODE>\state\ (copy ไปที่อื่น)
  • ได้ไฟล์ .plugin จากผู้ดูแลโดยตรง ไม่รับจากแหล่งอื่น

หลัง update — DBA ผู้ใช้

VERIFY
  • เวอร์ชัน kit\VERSION ตรงกับ plugin และ _kit_previous\ มีเวอร์ชันเก่า
  • config / work ยังอยู่ครบ และค่าไม่เปลี่ยน
  • smoke test: validate ไฟล์ล่าสุด 1 ไฟล์ + รัน daily → สถานะเทียบกับเมื่อวานต้องไม่เปลี่ยนแบบอธิบายไม่ได้
  • เปิดรายงาน H01 / X01 ได้ปกติ (Excel ไม่ขึ้น error, HTML แก้ไข/Save/Print ได้)
  • มีป้าย COLLECTOR → วางแผน deploy collector ใหม่ทุก server ตามหัวข้อ 2–3 (ใช้ CR)
  • scheduled task (ถ้ามี) รันรอบถัดไปสำเร็จ

หลัง update — Maintainer

FOLLOW-UP
  • ติดตามว่าทุกคนอัปเดตแล้ว (รายชื่อผู้ใช้ + เวอร์ชัน)
  • รวบรวมปัญหา 3–5 วันแรก ถ้าร้ายแรงให้สั่ง rollback ทันที
  • ติดตามการ deploy collector ของลูกค้าที่ได้รับผลกระทบ
  • รัน security_check.py กับ workspace ตัวอย่างก่อนแจกต่อ

6Rollback

ส่วนวิธี rollback
kit ใน workspaceพิมพ์ "rollback kit" หรือรัน python3 DBA_Ops\kit\tools\install_kit.py --workspace DBA_Ops --rollback (นำเวอร์ชันล่าสุดใน _kit_previous กลับมา)
plugin (skills)ติดตั้งไฟล์ .plugin เวอร์ชันก่อนหน้าทับ
collector บน serverคืนโฟลเดอร์ collector เดิมที่สำรองไว้ก่อน deploy · generator อ่านไฟล์ของ collector เวอร์ชันเก่าได้เสมอ (contract เดิม)
ข้อมูลรายงานคืน work\<CODE>\state\ จากที่สำรองไว้ แล้วรัน daily/monthly ใหม่

7ข้อห้าม

⛔
ห้ามแจก config\ / work\ ของลูกค้า · ห้ามใส่ password หรือ PAR URL ในไฟล์ที่แจก · ห้ามให้ Claude เชื่อมต่อหรือรัน change กับ DB ลูกค้าโดยตรง · ห้ามส่งรายงานให้ลูกค้าโดยไม่ผ่านการตรวจทานของ DBA · ห้ามแก้ template ต้นฉบับใน kit (ให้คัดลอกออกมาก่อน) · ห้ามรวม Oracle/reference ที่มีชื่อระบบของโปรเจกต์ใน plugin
