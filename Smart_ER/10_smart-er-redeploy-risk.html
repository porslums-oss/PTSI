Smart ER — ประเมินความเสี่ยง (Deploy ใหม่)

Smart ER — ประเมินความเสี่ยงและช่องโหว่ ก่อนสร้าง / Deploy ใหม่

ความเสี่ยงที่เกี่ยวกับตัวโค้ด สคริปต์ การ deploy และการย้ายระบบ พร้อมหลักฐานและแนวทางแก้

รายการทั้งหมด: 26สูง: 7กลาง: 13ต่ำ: 6อัปเดต: 2026-10-06
!
ข้อสรุปสำหรับการ deploy ใหม่สำคัญ
ระบบ พร้อมใช้ทดสอบด้วยข้อมูลจำลอง แต่ยัง ไม่พร้อมใช้กับข้อมูลผู้ป่วยจริง — 5 เรื่องที่ต้องปิดก่อน: (1) ควบคุมสิทธิ์ตามบทบาทไม่ครบ (S1) · (2) ไม่มีการจำกัดการเดารหัสผ่าน (S2) · (3) รหัสผ่านเริ่มต้นและรหัสที่ฝังในไฟล์สคริปต์ต้องหมุน (S3–S5) · (4) งาน partition ต้องมี cron (D5) · (5) ยังไม่เคยทดสอบกับอุปกรณ์จริง (R4)
วิธีประเมิน: ตรวจจากโค้ดและสคริปต์ในชุดส่งมอบ (server.js, config.js, db/*.sql, deploy/) และจากประสบการณ์ deploy จริง · ยังไม่ได้ทำ penetration test, การสแกนช่องโหว่ของโครงสร้างพื้นฐาน Vercel/Neon, หรือการตรวจ source ของ hl7-listener แบบละเอียด — ระดับความเสี่ยงเป็นการประเมินเบื้องต้น ส่วนความเสี่ยงด้านคลินิกและ PDPA ของระบบ ดูเอกสาร 04
1

ความมั่นคงปลอดภัยและช่องโหว่จากการตรวจโค้ดและสคริปต์

รหัสความเสี่ยง / ช่องโหว่หลักฐานระดับแนวทางแก้
S1ควบคุมสิทธิ์ตามบทบาทไม่ครบ — ผู้ที่ล็อกอินได้ทุกบทบาท (รวม VIEWER, REGISTER) เรียก endpoint เขียนข้อมูลได้ เช่น คัดกรอง, จำหน่าย, รวม HN, รับทราบ alarmserver.js ใช้ role() เพียง 9 endpoint (tv-link, hl7 test/device, terminals, settings) · 02_functions.sql ไม่มีการตรวจ roleสูงเพิ่มตารางสิทธิ์ role → function ใน DB (ตรวจใน fn_* แต่ละตัว) หรืออย่างน้อย role() ที่ทุก endpoint เขียน; ทดสอบด้วยบัญชี VIEWER
S2ไม่มีการจำกัดจำนวนครั้งล็อกอิน/ล็อกบัญชี — เดารหัสผ่านซ้ำได้fn_login ตรวจรหัสแล้วตอบ LOGIN_FAILED เฉย ๆ ไม่มีตัวนับ; ไม่มี rate-limit ใน Expressสูงเพิ่มตัวนับล้มเหลว+ล็อกชั่วคราวใน DB, rate limit ที่ nginx (limit_req) / Vercel Firewall, ความยาวรหัสผ่านขั้นต่ำและนโยบายเปลี่ยนรหัส
S3บัญชี/รหัสผ่านเริ่มต้นที่รู้กันทั่ว (admin/nurse01/reg01) และ .env.example มีรหัสตัวอย่าง04_seed.sql, .env.exampleสูงบังคับเปลี่ยนรหัสตอนติดตั้ง (checklist), ลบ/ปิด seed user ใน production, ห้ามใช้ค่า ChangeMe_*
S4รหัสผ่านจริงของ role บนฐานทดสอบฝังอยู่ในไฟล์สคริปต์ db/neon_editor/neon_1_roles_schema.sql ซึ่งอยู่ใน smart-er-postgresql.zip และโฟลเดอร์ E:\PTSIไฟล์ส่งมอบสูงถือว่ารหัสชุดนั้นรั่วไหลได้: หมุนรหัสผ่าน 5 role บน Neon ก่อนใช้งานจริง, อย่าแจกไฟล์/zip นี้ต่อ, ครั้งหน้าให้สคริปต์รับรหัสเป็นตัวแปรหรือสุ่มตอนรัน
S5รหัสผ่านของ neondb_owner เคยแสดงบนหน้าจอระหว่างตั้งค่าระหว่างการ deployกลางReset รหัสผ่าน neondb_owner ใน Neon Console; ใช้ role แยกสำหรับงานประจำ
S6TLS ไม่ตรวจใบรับรองฝั่ง DB (rejectUnauthorized:false) — เสี่ยง man-in-the-middle บนเส้นทาง Vercel→Neonconfig.js (สาขา DATABASE_URL)กลางใช้ sslmode=verify-full + CA ที่เชื่อถือ (Neon ใช้ CA สาธารณะ) เมื่อใช้งานจริง
S7/api/health เปิดสาธารณะและเปิดเผยเวลา DB + สถานะ HL7server.js ก่อน app.use('/api', auth)ต่ำคืนเฉพาะ {ok:true} ต่อภายนอก; รายละเอียดให้ ADMIN
S8รหัสเข้าจอ TV (TV_KEY) อยู่ใน URL — ติดอยู่ใน history/log และใช้ร่วมกันทุกจอ; ถ้าไม่ตั้ง /api/tv เปิดโล่งserver.js /api/tv, tv.htmlกลางตั้ง TV_KEY เสมอ + จำกัด IP ของจอที่ nginx (ตัวอย่างอยู่ใน nginx-smart-er.conf), หมุน key เป็นระยะ; ระยะยาวใช้ device token แบบ Tablet
S9Session token เก็บเป็นข้อความธรรมดาในตาราง app_session และใน sessionStorage ของเบราว์เซอร์ — ถ้า DB รั่วหรือเกิด XSS นำไปใช้ต่อได้ (หมดอายุ 12 ชม.)01_schema.sql, index.htmlกลางเก็บ hash ของ token (เหมือน device token), ลดอายุ session, เพิ่ม CSP header, คงการ escape ข้อมูลทุกจุด
S10HL7 listener รับ TCP โดยไม่ยืนยันตัวตน; HL7_ALLOW_IPS ว่าง = รับทุก IPconfig.js, hl7-listener.jsกลางตั้ง allow-list IP และ firewall เฉพาะ subnet ของ monitor, แยก VLAN อุปกรณ์การแพทย์
S11ไม่มี security header ครบ (CSP) ที่ชั้นแอป — มีเพียง nosniff, X-Frame-Options, Referrer-Policy; HSTS ขึ้นกับ nginx/Vercelserver.jsต่ำเพิ่ม CSP และ HSTS ที่ reverse proxy
S12ไม่ใช้ Row-Level Security — การแยกข้อมูลพึ่ง role/function ทั้งหมด; er_app อ่านตาราง hl7_message (ข้อความ HL7 ดิบ) ได้โดยตรง03_views_security.sqlต่ำประเมินจำกัด SELECT ตารางดิบเหลือเท่าที่จำเป็น; ตั้ง retention ของ raw message
2

การ deploy และการดำเนินงาน

รหัสความเสี่ยง / ช่องโหว่หลักฐานระดับแนวทางแก้
D1เปิดระบบทดสอบบนอินเทอร์เน็ตสาธารณะ (โดเมน production ของ Vercel เปิดสาธารณะ) — ใครก็เข้าหน้า login ได้โดเมน *.vercel.appกลางเปิด Vercel Authentication/Password Protection หรือ IP allow-list; ใช้ข้อมูลจำลองเท่านั้น
D2ข้อมูลจริงบนคลาวด์ต่างประเทศ (Vercel/Neon) — ขัดกับ PDPA/นโยบาย รพ. ถ้าไม่ประเมิน DPIA และข้อตกลงประมวลผลขอบเขตเอกสาร 09สูงห้ามใช้ข้อมูลผู้ป่วยจริงบนระบบทดสอบ; production ติดตั้งภายใน รพ.
D3HL7 ใช้ไม่ได้บน Vercel (TCP) — ทดสอบแบบ end-to-end ไม่ได้ในสภาพแวดล้อมคลาวด์server.js (VERCEL guard)กลางวาง listener แยกบน VM/คอนเทนเนอร์ที่รับ TCP แล้วต่อ Neon ด้วย er_hl7 (direct host)
D4ข้อจำกัดแพ็กเกจฟรี: cold start, Neon หลับ, โควต้า invocation เมื่อจอ TV/Tablet poll ถี่คู่มือ 09กลางเพิ่มช่วง poll, ตั้ง region ใกล้ DB (sin1), ใช้แพ็กเกจที่เหมาะสมหรือ server ภายใน
D5Partition รายเดือนต้องมีงานสร้างล่วงหน้า — ถ้าลืมแล้วข้อความ HL7/สัญญาณชีพเดือนใหม่จะเขียนไม่ได้fn_create_partitions (ไม่มี cron บน Neon/Vercel)สูงตั้ง cron/Task Scheduler (06_maintenance.sql) หรือ Vercel Cron; เพิ่ม monitoring แจ้งเมื่อ partition ถัดไปไม่มี
D601_schema.sql รันซ้ำไม่ได้ (CREATE TABLE ตรง ๆ) (เอกสาร 09 รุ่นเดิมระบุว่ารันซ้ำได้ ซึ่งไม่ถูกต้อง — แก้ไขแล้วในรุ่น 2026-10-06)01_schema.sql, 09กลางทำ migration แบบ versioned (ไฟล์ ALTER) แทนการรัน 01 ซ้ำ
D7แก้ Environment Variable แล้วลืม Redeploy / รหัสใน URL ไม่ตรง role → ระบบล่มเงียบ ๆ (พบจริงในโปรเจกต์บัญชี)ประสบการณ์ deployต่ำเพิ่มขั้น “ตรวจ /api/health หลัง deploy” ในทุกครั้ง
D8ไม่มีแผน backup/restore ที่ทดสอบจริงบน Neon (พึ่ง retention ตามแพ็กเกจ) และ backup.sh ทดสอบเฉพาะบนเครื่อง Linuxคู่มือ 07 หมวด Backupกลางตรวจนโยบาย PITR ของแพ็กเกจที่ใช้, ทดสอบ restore ลงฐานแยกทุกไตรมาส
D9Dependency และ runtime: ตอนนี้ npm audit ไม่พบช่องโหว่ (2 package) แต่ Node 22 มีวัฏจักร LTS ที่หมดอายุในอนาคตpackage.jsonต่ำตรวจ npm audit ทุกครั้งก่อน deploy; วางแผนอัปเกรด Node ตาม roadmap ทางการ

การสร้างระบบใหม่ / ย้ายระบบ

รหัสความเสี่ยง / ช่องโหว่หลักฐานระดับแนวทางแก้
R1ต้องสร้างระบบใหม่จากศูนย์ แต่ไม่มีเอกสาร/ไฟล์ครบเอกสารชุด 00–11 + ไฟล์ smart-er-postgresql.zipต่ำเก็บ repo (db/, app/, deploy/, docs/) ใน Git ส่วนตัว พร้อมเอกสารชุดนี้
R2ข้อมูลเดิมย้ายไม่ได้ / ไม่ตรงโครงสร้างใหม่—กลางส่งออกด้วย pg_dump + ทดสอบ restore บน staging ก่อนสลับระบบ; เก็บ dump ก่อน migration เสมอ
R3Deploy ใหม่แล้ว role/สิทธิ์ผิด (เช่น function owner ไม่ใช่ er_owner บน Neon)บทเรียนใน 08กลางใช้ชุดสคริปต์ neon_editor ที่ทดสอบแล้ว; ตรวจ pg_proc.proowner และ GRANT หลังติดตั้ง
R4อุปกรณ์จริง (monitor, สแกนเนอร์, ปริ้นเตอร์, Tablet) ยังไม่เคยทดสอบ — เจอปัญหาตอน go-liveคู่มือ 05 หัวข้อ 8, “ต้องยืนยันกับผู้ขาย”สูงทดสอบกับอุปกรณ์จริงตามรายการ 15 ข้อ ใน staging ของ รพ. ก่อนใช้งาน
R5ความรู้อยู่กับคนเดียว (bus factor)—กลางฝึกผู้ดูแลอย่างน้อย 2 คน ใช้คู่มือ 06 และ 07 เป็นหลักสูตร

Checklist ก่อน Deploy ใหม่

  • หมุนรหัสผ่านทุก role บน Neon และ neondb_owner (S4, S5)
  • เปลี่ยนรหัสผ่านทุกบัญชีผู้ใช้เริ่มต้น หรือปิดใช้ (S3)
  • ตั้ง TV_KEY เป็นค่าสุ่ม และจำกัด IP ของจอ (S8)
  • ปิดช่องว่างสิทธิ์ตามบทบาท และทดสอบด้วยบัญชี VIEWER/REGISTER (S1)
  • เพิ่ม rate-limit / ล็อกบัญชีที่ล็อกอิน (S2)
  • ตั้งงาน partition และ monitoring (D5)
  • เปิด Vercel Authentication หรือ allow-list สำหรับระบบทดสอบ (D1)
  • ยืนยันว่าไม่มีข้อมูลผู้ป่วยจริงบนคลาวด์ (D2)
  • ตั้ง sslmode=verify-full สำหรับ production (S6)
  • ทดสอบ restore จาก backup ลงฐานแยก (D8)
  • รัน npm audit และ smoke test ก่อน deploy (D9)
